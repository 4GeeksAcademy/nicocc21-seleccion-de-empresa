<p>Evidence-led performance optimization using real-user signals for prioritization and browser traces for diagnosis. Focuses on loading speed, runtime responsiveness, and resource delivery.</p>
<h2>How it works</h2>
<ol>
<li>If a page can run, read <a href="https://github.com/addyosmani/web-quality-skills/blob/HEAD/skills/performance/references/MEASUREMENT.md" target="_blank" rel="ugc nofollow noopener">the measurement workflow</a> and establish a field-plus-lab baseline before editing.</li>
<li>Prioritize poor real-user Core Web Vitals. Use a DevTools performance trace and its focused insights to find the cause.</li>
<li>Inspect and change only the code or assets connected to measured bottlenecks.</li>
<li>Re-run equivalent lab measurements and report before/after values, conditions, and uncertainty. Field verification remains pending until enough new user data arrives.</li>
</ol>
<p>When no runnable page exists, perform static inspection but call findings <strong>hypotheses</strong>, not measured regressions. Include the command or browser workflow that can verify each high-impact hypothesis.</p>
<p>Prefer a browser tool that records a performance trace and exposes focused insights. With Chrome DevTools MCP, use <code>performance_start_trace</code> and <code>performance_analyze_insight</code>; do not route performance through <code>lighthouse_audit</code>, which covers non-performance Lighthouse categories.</p>
